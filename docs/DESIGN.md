# 设计说明

这份文档解释 `dsh-session-manager-delete` 为什么这样写。README 只讲怎么用；这里讲删除顺序、失效边界和取舍。

## 1. 总体结构

插件是标准 DSH bundle，分两半：

| 文件 | 角色 |
| --- | --- |
| `lib/index.js` | 宿主半区：注册一条同源 HTTP 路由，负责预览、删除、登记清理和复核 |
| `lib/client.js` | 浏览器半区，可读源码：菜单、确认框、本地状态清理、列表刷新 |
| `lib/client.bundle.js` | 浏览器半区的构建产物；DSH 客户端模块系统只加载这个文件 |

浏览器半区通过 `fetch` 调宿主路由。没有用 `@Remote` 或动态包 `host.call`，因为同源路由形态稳定、可单测，而且本机其它插件已经在生产里走通这条路。

样式表由客户端自己插入 `<head>`，用 `data-plugin-css` 去重，卸载时收走。客户端服务目录里没有 `styles` 服务；依赖 `ctx.get('styles')` 会让整个模态层静默失效。

客户端 `inject` 只声明 `slots`。`contextMenus` 是可选依赖：老宿主没有这个服务时，插件回退到旧菜单座位；如果把它写成硬依赖，老宿主的客户端插件会永远不启动。

## 2. 删除顺序

删除严格按下面的顺序执行：

```text
预览（只读）
  → 归档/活动/注销能力/清单闸门
  → 关闭会话名下终端
  → 注销 ctx.sessions / ctx.agents
  → 复核宿主内存
  → 重新收集待删清单
  → 删投影缓存
  → 删对话日志
  → 复核磁盘
  → 摘工作区登记
  → 清悬空引用
  → 清浏览器本地状态
  → 重拉侧栏列表
```

### 2.1 先关终端，再注销内存

`terminals.list(owner)` 按**对象身份**匹配属主，而 owner 就是 `agents.get(id)` 返回的那个活对象。一旦注销，`agents.get(id)` 变成 `undefined`，终端就再也关不掉。终端服务自己的属主回收要等 Agent 释放，而那时日志已经没了。所以顺序必须是「关终端 → 注销」。

### 2.2 让宿主忘掉会话

侧栏会话列表来自 `sessionController.list()` → `sessionQuery.listSessions()`，它是 live 优先的：

```js
for (const header of persisted) records.set(header.id, { ... })
for (const session of this._ctx.sessions.list()) records.set(session.id, { ... })
```

只要宿主进程还记着这个会话，磁盘删没删它都会出现在侧栏里；工作区登记又被摘掉了，于是它渲染成「未分组」。刷新页面清不掉，只有重启 DSH 才消失。

客户端打开的会话挂在 `agents.resume()` 建出来的 Agent 上，属主是服务自己的 `ctx`，活到进程结束。插件拿不到那个发布句柄，官方也没有 `forget` / `evict` 接口。但两个注册表都留着官方自己的注销原语：

```js
store = new Map()
detachEntered(entry) { ... }  // 身份校验 → 删表 → 发配对 disposed 事件
```

`forgetSessions()` 用它，而不是硬删文件：

1. 未落盘的空白会话先 `sessions.flush(session)` 补写一次落盘，持久层随后丢掉 pending 记录；
2. 从 `ctx.sessions` 注销（侧栏列表的来源）；
3. 从 `ctx.agents` 注销（属主）；
4. 复核 `ctx.sessions.get(id)` / `agents.get(id)`：还记着就拒删，一个文件都不动。

形状守卫：两个注册表必须都是 `store` Map + `detachEntered`，否则拒删（fail closed）。宁可不让删，也不用不确定的方式硬来。

### 2.3 先删缓存，最后删日志

一个会话在磁盘上有两块属于自己的痕迹：

```text
$DSH_HOME/sessions/<工作区 slug>/<会话 id>/session.v4.jsonl.zstd   对话日志（唯一一份）
$DSH_HOME/storages/session_projcache/sessions/<id>.json            投影缓存（可由日志重建）
```

整个 `<会话 id>/` 目录递归删，所以同目录里的锁文件、迁移临时文件、发布临时文件、其他格式版本的日志会一起走。缓存那边连 `<id>.json.bak.<时间戳>` 备份一起清。

顺序是**先删投影缓存、最后删日志**。缓存可重建，日志不可重建；中途失败时，尽量保住一条完整、可重试的会话，而不是「日志没了、缓存和登记还在」的半吊子。

删完后，如果某个工作区 slug 目录确实变空，才收走它。只删「此刻确实为空」的目录，遇到任何别的条目就放手。

### 2.4 临时目录

工具输出溢出（spill）不在 `DSH_HOME` 下：

```text
<TEMP>/dsh-spill-<6 位>/session-<sha256(会话 id)[0:12]>/<随机名>-<名字>
```

目录名是会话 id 的 sha256 前缀，可计算，所以能精确指认。官方回收只看文件年龄（默认 30 天），会话删了它还在；插件按官方写死的两条形状正则把它一起清掉：

- 根名必须是 `dsh-spill-` + 6 位；
- 会话目录名必须正好等于目标会话算出来的那一个；
- 必须是真目录，软链/联接一律不碰。

spill 删除是尽力而为：删不掉不会把整次删除判成失败，但会如实报出来。

### 2.5 工作区登记

登记只通过官方服务接口摘除，绝不手改 `workspace.json`：

```js
await registry.unpinSession(sessionId)
await registry.unarchiveSession(sessionId)
await workspace.detachSession(sessionId)
```

顺序是「先抓引用、再删文件、最后摘登记」。`workspace.sessionIds` 是按 header 索引过滤的投影；日志一删，它就看不见这个会话了，那时再问「谁引用了它」只会得到空答案。所以删除前先把引用抓出来，删干净后再按 id 剪掉残留。

`workspaceRegistry` 的实体和全局状态都有内存缓存（`setState` 先写域再换缓存，`WorkspaceEntity` 缓存 `this.record`）。绕过它直写 `workspace.json` 会让内存与磁盘分叉，下一次任意登记写入就会把刚剪掉的 id 写回来——这正是「删完重启又冒出未分组」的来源。只有宿主完全没有注册表接口时，才退回直写，并在结果里说明。

### 2.6 浏览器本地状态

客户端清理规则来自官方 store 的真实契约：会话级键是 `${persist}.${scopeKey}`，`scopeKey` 就是会话 id。

| 键 | 处理 |
| --- | --- |
| `dsh.conversation.<id>` | 整键移除 |
| `dsh.user-questions.drafts.v1.<id>` | 整键移除 |
| `dsh.sidebar-browser.v1.<id>` | 整键移除 |
| `dsh.sidebar-right.v1.<id>` | 整键移除 |
| `dsh.schedule.task-tab.v1.<id>` | 整键移除 |
| `dsh.workspace.view.v5` | 只摘 `sessionOrderByAccount.*` 数组里的目标 id |
| `dsh.sessions.current` | 选中的会话本身被删 → `{}`；只有 `subagentAddress` 提到被删的子代理 → 只摘该字段 |
| 其他键 | 不动；值不是认识的 JSON 结构时只报告、不改写 |

判定不是前缀匹配：**键名里必须有一整段正好是会话 id** 才算会话私有键。这挡住了 `dsh.conversation.contentWidth` 这个陷阱——它和 `dsh.conversation.<id>` 共享前缀，按前缀扫会把用户的全局转录宽度偏好清掉。

删掉一个键之后，还活着的 store 可能在下一次状态变化时把它写回来。删除流程把本地清理排在宿主注销之后：会话已经不在宿主里，它的面板/页签作用域随之结束，键不会被再写回来。

### 2.7 重拉列表

宿主注销不会通知浏览器重拉会话列表。侧栏里的旧快照仍然留着这一行，而工作区登记已经摘掉了它，分组算法就把这条「不属于任何工作区」的旧行显示成「未分组」。

所以删除成功后客户端调用公开的 `ctx.sessions.refresh()` 重拉一次权威列表。`refresh()` 有 single-flight：如果列表请求正在飞，它可能复用旧请求；客户端会再刷新一次，并用 `sessions.list.getSnapshot().byId` 检查目标 id 是否真的消失。

重拉失败不算删除失败：文件已经删了，完成页会写「侧栏列表没有刷新成功……刷新页面就会消失」。

## 3. 删除集合与血缘

### 3.1 子代理会话

`origin === 'subagent'` 的会话目录名是不带前缀的裸 uuid，侧栏里根本看不见。删父会话时必须一起删，否则它们会变成磁盘上永远无人认领的孤儿。

名单来自两条证据的并集：

1. 日志 header 里的父指针 `parentSession`（广度优先，可以往下走多层）；
2. 子代理目录投影 `subagents.listDescendants()`。有些子会话的 header 读不出来（目录损坏、模式不认识），只有这条投影能点名它们。

投影报出的「读不出目录」分支会写进确认框提醒，因为那下面可能还有更深的子会话数不到。

### 3.2 fork

fork 出来的可见会话默认不删，而且在血缘遍历里不再往下走：fork 自己的子代理会话属于那段会话。想连它一起删，就在确认框的可选列表里勾它；勾了才会连它自己的子代理会话一起删，而且它自己也得是已归档的。

### 3.3 悬空引用

工作区登记里指向「已经不存在的会话」的 id，就是界面上那些残留的「未分组」条目。预览会列出来；用户确认删除时，这些 id 会跟着一起从登记里剪掉。

预览与执行不是同一份盲目清单：删除前会重新验证一遍。从「看一眼」到「点确认」之间，会话可能又回来了，那就不能再剪。剪之前还会和当前的悬空集合求交集，只剪仍然真的悬空的 id。

不想等到下一次删除，就在预览里点「现在清理」：它只走登记的官方接口，不删任何会话。一次最多 200 条，超出会明确写「另有 N 条这次没有列出」；形状不合法或超限的请求会被宿主直接拒掉（400），不会静默丢掉。

### 3.4 并发删除

删父会话会连带子代理，而子代理也可能被单独删。只锁根会话会让两次删除的目标集合重叠、互相删对方的文件。

所以最终目标集合算出来后，先用一个进程内 `Set` 同步检查并占住全部 id：

- 冲突：409，一个文件不动；
- 成功：整批占住，结束后释放；
- 同一会话重复提交：409「这个会话正在删除中」。

## 4. 安全闸门

1. **身份**：会话 id 必须匹配小写 `(session-)?<uuid>`。斜杠、`..`、盘符、大小写变体一律进不来。拼出的路径再验三次：字符串意义上位于会话根内 → lstat 确认是真目录、不是软链/联接 → realpath 后仍在会话根内。
2. **归档**：只删已归档会话。归档状态从持久化记录 `global.archivedSessionIds` 读；读不到就拒删（fail closed）。
3. **活动**：优先问官方 `workspace/session-activity` 瀑布，对删除集合里每个会话各问一次。瀑布不可用时退回 `sessionController.list()` + `jobs`。查不到状态就拒删。有工作在跑时，界面给一个默认勾选的「先停掉」，提交带 `stop` 才放行；停完重新验一次。
4. **注销能力**：进程还记着会话时，必须先确认两个注册表都具备 `store` + `detachEntered`；未落盘的空白会话还要求 `sessions.flush` 可用。否则拒删。
5. **确认**：POST 必须带 `confirm: 'delete-session'`；界面还有一道必须勾选的确认框，`confirm()` 里再查一次。
6. **同源**：`Sec-Fetch-Site` 只接受 same-origin/none；删除请求要求 `Origin` 与 `Host` 同源、不接受 `Origin: null`，并且 Host 必须是 IP 字面量或 localhost（挡 DNS rebinding）。
7. **只删说明过的**：路径只有两个来源——持久化后端自己指认的 `sessionPersistence.locate(header)`（还要过基名、真目录校验），以及扫 `sessions/` 反查出来的（取并集）。终端只关目标会话名下、属主确实是它的那些；登记只摘目标 id；本地状态只动目标 id 的键与引用；悬空引用只剪给用户看过的那几条。
8. **复核**：注销后复核内存，删完扫盘复核，摘完复核登记。只有三份复核都过了才回 200。

## 5. 失败语义

| 状态 | 什么时候 | 意味着什么 |
| --- | --- | --- |
| 400 | id/请求体/清单形状不对，或超过 200 条 | 什么都没动 |
| 403 | 跨站或 Host 不是 IP 字面量 | 什么都没动 |
| 404 | 会话已经不存在 | 没什么可删的 |
| 409 | 没归档、注销能力不可用、注销没生效、还有工作在跑且没停、目标超过 200 | 文件与登记保持原样，可以重试 |
| 413 | 请求体过大 | 什么都没动 |
| 500 | 文件没删净 | 已删文件不可恢复；登记保持原样，但终端可能已关、宿主内存已注销；残留路径逐条列出 |

有两类东西刻意不算失败、但会具名报出来：

- `spillRemaining`：临时目录里的工具输出溢出，官方自己按 30 天回收；
- `memoryRemaining`：删完才发现宿主还留着记录的竞态。

文件那时已经删了，把它们算成「失败」反而是另一种谎话。

## 6. 为什么不用别的方案

- **为什么用 HTTP 路由，而不是 `@Remote` / `host.call`**：同源路由形态稳定、可单测；`@Remote` 的装饰器导入路径和动态包 `host.call` 的宿主侧契约在本机没有可读样例。
- **为什么样式表自己插**：客户端没有 `styles` 服务。按官方打包插件的做法自己插 `<style>`，用 `data-plugin-css` 去重。
- **为什么删文件必须自己动手**：DSH 没有删除会话的服务接口（`sessionPersistence` 只有 create/open/stat/list/flush，`workspaceRegistry` 只有 archive/attach 系列）。策略是「状态问服务，文件才自己删」，删除范围只用固定规则拼出来，不扫不猜。
- **为什么引用要在删文件之前抓**：投影按 header 索引过滤，日志一删就查不到引用。
- **为什么删干净才摘登记**：先摘登记会留下「界面里没有、磁盘上还在」的孤儿文件；失败的会话留在侧栏里还能重试。
- **为什么共享键只做定点摘除**：`dsh.workspace.view.v5` 里同时存着分组、排序、归档过滤、展开状态和每个会话的手工顺序。整键清掉会抹掉用户对其他会话的排序偏好。
- **为什么 `dsh.sessions.current` 分两种情况清**：选中的会话本身被删时退回 `{}`；只有 `subagentAddress` 提到被删子代理时，只删这个字段、保留父会话的选中。半截地址会被应用当成有效地址去恢复。
- **为什么并发删除要占住整批目标**：见 3.4。
- **为什么血缘要两条证据取并集**：header 读不出来时，只有目录投影能点名那条子会话；漏了它就是永久孤儿。
- **为什么「还有工作在跑」不再是硬闸门**：用户已经决定要删了，再让他回去找停止按钮只是把危险动作拆成两步。现在把「在跑什么」摆出来 + 默认勾选「先停掉」，停完再验一次。
- **为什么 GET 一点都不写**：写入只能发生在用户明确点头之后。旧版本「顺手清扫」把一次只读查看变成了没人确认过的改动。
- **为什么 spill 失败不算删除失败**：spill 是临时缓存，官方按 30 天回收；让一个临时文件把整次删除判失败，进而把登记留在那儿，代价远大于收益。
- **为什么未落盘的空白会话要先 flush**：那种会话只在持久层的 pending 内存表里，写句柄一关才会消失；先补写一份落盘，pending 记录随之丢弃，补写出来的文件再跟其它文件一起删。
- **为什么删除前要重新盘一次待删清单**：补写落盘会造出一份新日志，那份文件必须也在清单里，否则复核会报「删不干净」。

## 7. 验证

`scripts/verify-host.mjs` 在临时 `DSH_HOME` 里搭真实形状的夹具，覆盖：

- 归档闸门、活动闸门、注销形状闸门；
- 注销前后复核、未落盘会话 flush、disposed 事件；
- 子代理与 fork 血缘、并发删除；
- 悬空引用预览与清理、200 条上限、形状非法回 400；
- 软链/联接、被占用文件、删 A 不动 B；
- 删完扫盘、登记复核、失败语义。

`scripts/verify-client.mjs` 在微型 React、假 DOM、会记账的 localStorage 里跑构建产物，覆盖：

- 菜单注册、归档过滤、旧座位回退；
- 确认框、勾选、删除、取消、Esc、焦点归还、卸载清理；
- 本地状态清理的四条硬规则；
- 超时、迟到响应、repair 并发、fork 提示。

CI 用 Node 22 + Windows，先跑 `npm run check:bundle` 防止 `client.bundle.js` 漂移，再跑两套验证。
